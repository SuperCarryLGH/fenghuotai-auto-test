## 三、核心设计决策（贯穿全部脚本）

1. **by_account 关联**：老库 wallet.owner_id / user_address.account_id / order.account_id 都是 `sys_user.account_id`(UUID) → 统一映射到新 member_user.id
2. **ID 生成**：与 dev 同构 snowflake（epoch 1288834974657，`<<22`，19位）；`preload_used_ids` 预加载 dev 真实表+线上xlsx ID → `gen_id()` 不碰撞；`check_id_collision` 自动重分配并级联引用
3. **断点续传**：每表独立 `.migrate_state.json`（四表）/ `.migrate_dist_state.json` / `.migrate_order_state.json`；重跑前 `check_complete` 完整性校验；订单脚本有"试运行遗留+无断点→强制--reset"防重复保护
4. **已存在用户**（330个）：钱包**继承线上 wallet_id + 余额累加**（dev现有+老库，保留负）、流水/地址继承 user_id；无目标钱包则新建
5. **金额单位**：老元→dev分 ×100（钱包/流水）；订单 pay_money 元直接写 total_price/pay_price（保留2位）
6. **时间占位**：老系统 `1970-01-01` 占位 → **NULL**（订单 receive/recycle/weight/inspect_time；开发确认）
7. **污染过滤** `_is_polluted`：union select / jndi / sleep( / md5( / %bf / 0x / limit# 特征 → 整行跳过（地址496条、订单0条）
8. **影子表对齐线上**：`CREATE TABLE LIKE` 后 `_DROP_COLS`（member_user 19列、pay_wallet deposit_price）；临时中转列存老 UUID（member_user 的 `operation_center_uuid`、recycle_order 的 `operation_center_uuid`/`order_id_old`），同步时排除
9. **未映射列**：NOT NULL 按 dev 约定填（level_id=1、status 1→0、clear_status=0、address_id=0、creator/updater='migrate'、deleted=0、tenant_id=1），可空列→NULL
10. **后置处理**：operation_center_id 按**老 UUID**（线上分拣中心映射表老系统id）回填（不依赖 station 表）；sync_action 标记同步方式

## 九、全量模拟经验与注意事项（2026-08 本地库全量模拟沉淀）

### 1. 执行方式
- 全量必须 **nohup 后台跑**（`scripts/run_full_migration.sh` 编排器：分阶段日志 + exit 码检测，失败即止）
- **不要前台长跑**（会超时/被中断）；监控用「轮询 master.log + 查 dev 影子表行数」
- Python 输出重定向到文件是**块缓冲**（不逐行刷），日志长时间为空属正常，别误判卡死

### 2. 分销 parent 回填（重大坑，已修复）
- `pymysql.executemany` 对 **UPDATE 是逐行执行** → 42.7 万次到远程 RDS 的独立往返，实测**完全卡死**（90 秒 0 进展）
- 已改为：临时表 `_tmp_parent` + 批量 INSERT（multi-values）+ 一次 JOIN UPDATE，秒级完成
- **原则**：对远程库的大批量 UPDATE 严禁逐行 executemany；INSERT 用 multi-values 批量

### 3. 断点/幂等限制
- `migrate_dist` 的 parent 回填在 `st["done"]` 之前；中断后重跑会因当次内存 `promoter_id_map` 为空而**丢失 parent** → 只能整体 `--reset` 分销重跑（~9 分钟）
- 任何「后置回填依赖当次内存映射」的逻辑，中断后不能简单续跑，需整体重置

### 4. 四表「跳过」阶段仍慢
- `migrate_old_db_to_shadow.py` 无条件 `rebuild_by_account` 跑两次 + `check_id_collision` 加载 320 万 id
- 全量重跑（已 done）时 01_four_table 仍耗 ~8 分钟纯属无用功；**正式迁移前建议优化为只重建一次**

### 5. SQL 正则参数化
- REGEXP 模式串必须用 **`%s` 参数传递**；内联到 SQL 字符串字面量会被 MySQL 转义破坏（`\(`→`(`，报 "Mismatched parenthesis"）

### 6. QA 关联校验的 JOIN 陷阱
- 一订单多明细场景下，按 order_id 做 item×package 交叉 JOIN 会报**假不一致**（本次 274,694 条假阳性）
- 正确做法：双向校验「每个子行 (order_id,key) 有父行 + 每个父行有子行」

### 7. 环境预检
- dev/线上 RDS **IP 白名单**确认（公网 IP 会变，本次 123.160.230.114）；内存需 ≥3G 空闲（峰值 1.6-2.2G，跑前关 PyCharm/浏览器）；磁盘充足

### 8. 数据语义提醒
- 老库**空串 vs NULL 要区分**：`operation_center_uuid=''`（非 NULL）会让「有 UUID 未回填」误报，属正常
- 线上已存在用户的钱包/地址 `user_id` 不在影子表属**设计**（继承线上 id），QA 别当缺失
